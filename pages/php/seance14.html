01

Pourquoi la sécurité ? Les 3 grandes menaces

Tout ce qui arrive dans un script PHP — $_GET, $_POST, $_COOKIE, les en-têtes HTTP — est totalement contrôlé par le visiteur. Un utilisateur ne « remplit » pas toujours votre formulaire : il peut envoyer ce qu'il veut avec curl. La règle d'or est donc : ne jamais faire confiance aux entrées.

Trois familles d'attaques représentent l'essentiel du risque pour une application apprise jusqu'ici :

AttaqueSurface touchéeImpact
Injection SQLRequêtes construites par concaténationLecture / destruction de la base, contournement des connexions
XSSHTML affiché qui contient l'entrée utilisateurVol de session via du JavaScript injecté, défiguration
CSRFFormulaires / actions sans vérification d'origineActions effectuées à l'insu de l'utilisateur connecté
🛡️
Analogie : la porte du studio et la concierge

Votre application est un studio. La donnée entrante, c'est le courrier qu'on glisse sous la porte : il peut contenir un colis… ou un scorpion. Une bonne séquence de sécurité ressemble à un protocole de contrôle : filter_var inspecte le colis à l'entrée (validation), la requête préparée empêche que son contenu atteigne « le mur porteur » de la base (paramètres SQL), et htmlspecialchars neutralise les objets coupants avant l'affichage (échappement).

02

Injections SQL : requêtes préparées

Si la valeur saisie est collée directement dans la requête, le visiteur peut « casser » le texte SQL et pénétrer dans son code : c'est l'injection SQL, la faille n°1 du web historique.

PHP — ❌ à ne jamais faire 
<?php
  // ⛔ VULNÉRABLE : concaténation de l'entrée
  $login = $_POST['login'];
  $sql = "SELECT * FROM users WHERE login = '$login'";
  // Si $login vaut  ' OR 1=1 --  la requête devient :
  // SELECT * FROM users WHERE login = '' OR 1=1 -- "
  // → retourne TOUS les utilisateurs !
?>
CONSÉQUENCE

Connexion accordée à n'importe qui.
La base, telle qu'elle a été pensée, est contournée.

La solution : une requête préparée. Le SQL est envoyé d'abord (il est compilé tel quel), puis la donnée arrive séparément via un paramètre — elle ne peut plus être interprétée comme du SQL.

PHP — ✅ PDO + prepare/execute 
<?php
  $pdo = new PDO("mysql:host=localhost;dbname=site;charset=utf8mb4", "root", "");
  $pdo->setAttribute(PDO::ATTR_EMULATE_PREPARES, false);

  $stmt = $pdo->prepare("SELECT id, nom FROM users WHERE login = :login");
  $stmt->execute(["login" => $_POST['login']]);
  $user = $stmt->fetch(PDO::FETCH_ASSOC);

  if ($user) {
    echo "Bienvenue, " . htmlspecialchars($user['nom']);
  } else {
    echo "Login inconnu";
  }
?>
RENDU

Bienvenue, Nadia

⚠️
Pas d'exception : JAMAIS de concaténation

Un "... WHERE id = $id" est dangereux même si la valeur vient de $_GET['id'], d'un cookie, ou d'une « aide JS ». Toute donnée externe passe par un placeholder (:param ou ?) + execute([...]) — sans exception, y compris dans les ORDER BY que l'on liste par liste blanche d'un tableau constant.

Le placeholder ne transporte que des valeurs, jamais la structure SQL : écrire ORDER BY :col ou FROM :table échoue — erreur immédiate avec ATTR_EMULATE_PREPARES désactivé, tri silencieusement faux sinon, car le paramètre est cité comme une chaîne constante. Quand le visiteur choisit la colonne de tri, validez son choix dans une liste blanche (in_array($col, ["nom", "note"], true)) et n'insérez que la valeur approuvée dans le texte SQL. Règle mnémotechnique : au visiteur les données via :param, à vous la structure via une liste blanche.

03

XSS : échapper avec htmlspecialchars()

Si une saisie contient du HTML/JavaScript et est affichée tel quel, le navigateur l'exécute : on peut voler le cookie d'un visiteur avec document.cookie, rediriger la page, injecter un faux formulaire. C'est le XSS (Cross-Site Scripting). Le remède est l'échappement à l'affichage.

PHP — htmlspecialchars() 
<?php
  // Invitation malveillante postée :
  // <script>alert('cookie volé')</script>
  $commentaire = $_GET['commentaire'];

  echo htmlspecialchars($commentaire, ENT_QUOTES, 'UTF-8');
?>
RENDU

<script>alert('cookie volé')</script>
(affiché en texte — le script ne s'exécute pas)

Les caractères <, >, &, " et ' deviennent leurs entités HTML : le code est visible en texte mais ne sera jamais interprété. L'échappement s'applique à la sortie, à chaque affichage, même sur des données venues de la base.

💡
Toujours les 3 arguments

ENT_QUOTES traite aussi les guillemets simples (sinon un attribut onclick='…' peut passer), et l'argument 'UTF-8' fixe l'encodage attendu : certains encodages multi-octets historiques permettaient de dissimuler des caractères spéciaux. À l'inverse, strip_tags() seul ne suffit pas, car un XSS peut exister sans aucune balise (<img onerror=…> n'est qu'un exemple parmi d'autres).

⚡ EXO FLASH Le script qui n'exécute pas
  1. Créez flash_xss.php : affichez $_GET["msg"] ?? "bonjour" brut, puis la même variable passée dans htmlspecialchars($msg, ENT_QUOTES, "UTF-8").
  2. Appelez la page avec ?msg=<b>bonjour</b> : prévoyez la différence entre les deux lignes (gras ? balises en texte ?), puis vérifiez.
  3. Tapez ?msg=<script>alert(1)</script> : confirmez qu'aucune alerte ne s'ouvre sur la version échappée, et affichez un message « ça contenait du HTML » quand l'entrée change après échappement.
Voir un début de correction 
<?php
  $msg = $_GET["msg"] ?? "bonjour";
  echo $msg . "<br>";
  $safe = htmlspecialchars($msg, ENT_QUOTES, "UTF-8");
  echo $safe . "<br>";
  echo ($msg === $safe) ? "Rien à échapper" : "Ça contenait du HTML";
?>
04

CSRF : token de formulaire

Le CSRF (Cross-Site Request Forgery) abuse du fait que le navigateur envoie automatiquement les cookies de la session, même quand la requête vient d'un site externe. Une page malveillante peut très bien soumettre un formulaire vers votre site pendant que l'utilisateur est connecté : il suffit d'une <img src="http://votresite.test/avis"> cachée ou d'un formulaire auto-posté. La protection : associer à la session un token aléatoire inséré en champ caché, et re-vérifier ce token à chaque POST. Le pirate peut poster, mais jamais lire votre token : sans la bonne valeur, la requête est rejetée — hash_equals() compare en temps constant face aux timing attacks.

PHP — token CSRF 
<?php
  session_start();

  // 1) Générer le token une fois par session
  if (empty($_SESSION['csrf'])) {
    $_SESSION['csrf'] = bin2hex(random_bytes(32));
  }
  $csrf = $_SESSION['csrf'];
?>
<form method="post" action="traiter.php">
  <input type="hidden" name="csrf" value="<?php echo $csrf; ?>">
  <input type="text" name="message">
  <button>Envoyer</button>
</form>
<?php
  // 2) Dans traiter.php : refuser tout autre envoi
  if (!isset($_POST['csrf']) || !hash_equals($_SESSION['csrf'] ?? '', $_POST['csrf'])) {
    http_response_code(403);
    exit("CSRF : requête refusée");
  }
  echo "Requête légitime ✔";
?>
RENDU

Requête légitime ✔

05

Mots de passe : hash, jamais en clair

Un mot de passe ne doit jamais être stocké en clair, ni « chiffré » de façon réversible. On calcule un hash lent et salé avec password_hash(), qui embarque automatiquement un algorithme fort (PASSWORD_DEFAULT : bcrypt et ses successeurs), un salt aléatoire et un coût (facteur de lenteur). La vérification utilise password_verify().

PHP — password_hash / verify 
<?php
  // À l'INSCRIPTION
  $mp = $_POST['motdepasse'];
  $hash = password_hash($mp, PASSWORD_DEFAULT, ['cost' => 12]);
  // → enregistrer $hash en BDD (60 caractères env.)

  // À la CONNEXION
  $hashStocke = '$2y$12$eImiTXuWVxfM37uY4JANjQ...';
  if (password_verify($_POST['motdepasse'], $hashStocke)) {
    echo "Connecté : mot de passe correct";
  } else {
    echo "Identifiants invalides";
  }
?>
RENDU

Connecté : mot de passe correct

🚨
Ne JAMAIS utiliser md5() / sha1() pour les mots de passe

md5() et sha1() sont rapides à calculer (des milliards de hash/s sur GPU) et conçus pour l'intégrité de fichiers, pas pour les secrets : des Tables arc-en-ciel publiques cassent les plus courants en quelques secondes. C'est la faille « classique » des vieux tutoriels : WHERE mdp = md5($mp). Ne stockez jamais le résultat de md5() ou sha1() pour un mot de passe : utilisez uniquement password_hash(), qui indique lui-même son algorithme dans la chaîne produite (ex. $2y$12$ pour bcrypt).

⚡ EXO FLASH Deux hash, deux visages
  1. Dans flash_hash.php, affichez password_hash("2020", PASSWORD_DEFAULT) deux fois de suite : prévoyez — les deux chaînes sont-elles identiques ? — puis vérifiez.
  2. Contrôlez avec password_verify("2020", $h2), puis affichez strlen($h1) : quelle taille de colonne VARCHAR en déduit-on pour la BDD ?
  3. Affichez substr($h1, 0, 4) : quel algorithme le préfixe annonce-t-il, et pourquoi md5("2020"), lui, sera toujours identique à chaque appel ?
Voir un début de correction 
<?php
  $h1 = password_hash("2020", PASSWORD_DEFAULT);
  $h2 = password_hash("2020", PASSWORD_DEFAULT);
  echo $h1 . "<br>" . $h2;  // différents : salt aléatoire
  echo "<br>verify : " . (password_verify("2020", $h2) ? "OUI" : "NON");
  echo "<br>longueur : " . strlen($h1);    // 60 → VARCHAR(255)
  echo "<br>algo : " . substr($h1, 0, 4);  // $2y$ = bcrypt
?>
06

Valider les entrées & checklist finale

La validation rejette ce qui est inattendu dès l'entrée. filter_var() fournit des filtres prêts à l'emploi : e-mail, entier, URL… La stratégie gagnante est la liste blanche : « j'accepte exactement ceci » plutôt que « je cherche et retire le mal ».

PHP — filter_var() 
<?php
  $email = $_POST['email'] ?? '';
  $note  = $_GET['note']   ?? '';

  if (filter_var($email, FILTER_VALIDATE_EMAIL)) {
    echo "E-mail valide : $email<br>";
  }

  $note = filter_var($note, FILTER_VALIDATE_INT,
          ['options' => ['min_range' => 0, 'max_range' => 20]]);
  if ($note !== false) {
    echo "Note : " . (int)$note;
  }
?>
RENDU

E-mail valide : amina@cetemoh.com

Une arborescence propre

Structurez le projet avec index.php et public/ (seule racine servie par Apache), config/config.php (DSN et identifiants, rien de public), src/ (classes et dépôts PDO) et templates/ (vues échappées). Seul public/ est exposé : le code et la config restent inaccessibles au navigateur.

🧩
La checklist avant mise en ligne

1) requêtes préparées partout · 2) htmlspecialchars à chaque affichage · 3) token CSRF sur tout POST · 4) password_hash + password_verify · 5) validation en liste blanche des entrées · 6) erreurs PHP désactivées en production (display_errors=0) · 7) config hors racine web, jamais versionnée avec les identifiants réels.

07

Exercices pratiques

EX 01 💉 Démonstration d'injection et réparation
  1. Écrivez exo_login_vuln.php avec la requête concaténée "SELECT id FROM users WHERE login = '$login'" (base locale de la séance 12).
  2. Postez ' OR 1=1 -- comme login et observez que « la connexion s'effectue ».
  3. Réécrivez le fichier en version préparée :login ; rejouez la même saisie → aucun utilisateur trouvé.

Indice : gardez le même formulaire ; seul le traitement change (prepare() + execute([…])).

EX 02 💬 Livre d'or sans XSS
  1. Créez exo_livredor.php : un formulaire POST «pseudo» + «message», listé sous le formulaire.
  2. Insérez un commentaire piège : <script>alert('XSS')</script>.
  3. Échappez pseudo et message à l'affichage avec htmlspecialchars(..., ENT_QUOTES, 'UTF-8') et vérifiez que le script reste du texte inerte.

Indice : on échappe à la sortie, avant l'echo — pas besoin de nettoyer à la sauvegarde.

EX 03 🎫 Formulaire blindé par token
  1. Partez d'un formulaire de contact POST. Ajoutez session_start() et la génération du token si absent (bin2hex(random_bytes(32))).
  2. Ajoutez le champ caché <input type="hidden" name="csrf">.
  3. Dans le script de traitement, refusez avec http_response_code(403) + exit si hash_equals() échoue ; testez en supprimant le champ.

Indice : comparez toujours avec hash_equals($session, $post) — c'est la fonction prévue pour la vérification de secrets.

EX 04 🔑 Inscription / connexion avec password_hash
  1. Créez une table users(id, login, mdp_hash) et « inscrivez » deux comptes avec password_hash($mp, PASSWORD_DEFAULT, ['cost' => 12]).
  2. Dans la partie connexion, récupérez le hash (requête préparée !) puis validez avec password_verify().
  3. Ajoutez la validation de l'entrée : login non vide, filtré ; mot de passe neuf au moins 8 caractères.

Indice : envoyez le message identique « Identifiants invalides » que le login existe ou non : ne révélez pas quel champ est incorrect.

08

Bilan & mini-glossaire

Ce que vous maîtrisez

  • Comprendre que toute entrée est hostile ($_GET, $_POST, cookies…)
  • Éliminer l'injection SQL avec PDO prepare / execute
  • Neutraliser le XSS avec htmlspecialchars(…, ENT_QUOTES, 'UTF-8') à l'affichage
  • Protéger chaque POST par un token CSRF vérifié par hash_equals()
  • Stocker les mots de passe avec password_hash() et les vérifier avec password_verify()
  • Valider les entrées en liste blanche avec filter_var()
  • Organiser un projet (config/, src/) pour ne pas exposer le code
  • Appliquer la checklist complète avant une mise en ligne
🚨
Erreurs fréquentes
  • Concaténer une donnée dans le SQL « juste pour un id » → injection SQL.
  • Faire confiance à la base de données : une donnée stockée doit être échappée à l'affichage.
  • Utiliser strip_tags() seul et croire que ça protège → des XSS passent sans balise.
  • Hasher avec md5() ou sha1() → craquage quasi instantané.
  • Générer le token CSRF à chaque rechargement sans le stocker → formulaire invalide à chaque fois.

Mini-glossaire

Injection SQL
Faille où une donnée externe est interprétée comme du SQL ; traitée par requêtes préparées.
Requête préparée
SQL envoyé d'abord, paramètres envoyés séparément via placeholders.
XSS
Cross-Site Scripting : HTML/JS injecté dans une page affichée ; traité par htmlspecialchars().
Échappement
Transformation des caractères spéciaux (<, >, ", ', &) en entités.
CSRF
Cross-Site Request Forgery : requête soumise à l'insu de l'utilisateur connecté.
Token CSRF
Valeur aléatoire stockée en session, envoyée en champ caché et vérifiée par hash_equals().
password_hash
Hash de mot de passe lent et salé (PASSWORD_DEFAULT, paramètre cost).
Validation
Rejet des entrées inattendues, de préférence en liste blanche (filter_var()).
