01

Le formulaire HTML

Un formulaire est un bloc HTML <form> qui regroupe des champs de saisie (<input>, <select>, <textarea>) et les envoie vers une page cible au clic sur le bouton. Deux attributs du <form> pilotent l'envoi : action (la page qui recevra les données) et method (la façon de les transporter). Chaque champ doit impérativement porter un attribut name : c'est par ce nom que PHP retrouvera la valeur.

HTML — inscription.html 
<form method="post" action="traitement.php">
  <label>Nom
    <input type="text" name="nom" required>
  </label>
  <label>E-mail
    <input type="email" name="email" required>
  </label>
  <label>Classe
    <select name="classe">
      <option value="a2">Année 2</option>
      <option value="a3">Année 3</option>
    </select>
  </label>
  <button>S'inscrire</button>
</form>
RENDU

Formulaire d'inscription : trois champs (Nom, E-mail, Classe) et un bouton « S'inscrire ». À la soumission, le navigateur envoie nom, email et classe vers traitement.php.

📝
method et action, pas à pas

action : l'URL qui reçoit les données ; omise ou vide, c'est la page actuelle qui se reçoit elle-même — pratique pour valider et afficher dans le même fichier. method : post place les données dans le corps de la requête HTTP (invisible, pas de limite pratique) ; get les accroche à l'URL, visibles par tout le monde. Absent, le navigateur utilise get par défaut.

02

Récupérer les données

Côté PHP, les données envoyées arrivent dans des superglobales : des tableaux associatifs toujours disponibles, dans toutes les portées. La clé est l'attribut name du champ, la valeur sa saisie. Tous les champs renvoyés sont des chaînes : un <input type="number"> fournit quand même "25", qu'il faudra convertir ou valider.

PHP — traitement.php 
<?php
  if ($_SERVER["REQUEST_METHOD"] === "POST") {
    $nom    = $_POST["nom"];
    $email  = $_POST["email"];
    $classe = $_POST["classe"];

    echo "Bonjour " . $nom . "<br>";
    echo "Votre e-mail : " . $email . "<br>";
    echo "Classe : " . $classe . " ";
    echo "(type PHP : " . gettype($email) . ")";
  }
?>
RENDU

Bonjour Ali
Votre e-mail : ali@mail.ma
Classe : a2 (type PHP : string)

SuperglobaleMéthode HTMLVisibilité des données
$_GETmethod="get" (ou liens / URL directe)visibles dans l'URL, partagables, historisées
$_POSTmethod="post"invisibles dans l'URL, corps de la requête
$_REQUESTles deux à la foisfusion de $_GET et $_POST — usage déconseillé
📝
Le test de méthode d'abord

Encadrez toujours le traitement par if ($_SERVER["REQUEST_METHOD"] === "POST") : sans lui, la première visite de la page (sans soumission) déclencherait des erreurs « undefined index ». L'attribut name est le seul lien entre le HTML et la superglobale — un champ sans name n'est jamais envoyé à PHP.

⚡ EXO FLASH Bonjour, inconnu
  1. Créez recap.php : un formulaire GET qui s'auto-envoie, avec deux champs name="prenom" et name="ville".
  2. Sous le formulaire, lisez les deux clés dans $_GET et affichez « Bonjour X, belle ville que Y ».
  3. Prévoyez ce que rend la page ouverte sans aucune saisie, puis vérifiez : sans ?? PHP avertit « Undefined array key », et avec gettype($prenom) vous constaterez que la valeur reste toujours une string.
Voir un début de correction 
<?php
  $prenom = $_GET["prenom"] ?? "visiteur";
  $ville  = $_GET["ville"] ?? "inconnue";

  echo "Bonjour $prenom, belle ville que $ville<br>";
  echo "Type de prenom : " . gettype($prenom);
?>
03

Valider les saisies

Les attributs HTML (required, type="email") ne sont qu'un confort pour l'utilisateur : n'importe qui peut envoyer en Postman une requête forgée avec un e-mail vide ou absurde. La validation côté serveur est la seule qui compte. On y combine isset (la clé existe), empty (valeur vide), trim (espaces parasites) et filter_var (format).

PHP — Validation complète 
<?php
  $erreurs = [];

  $nom = trim($_POST["nom"] ?? "");
  $email = trim($_POST["email"] ?? "");
  $age = $_POST["age"] ?? "";

  if ($nom === "") {
    $erreurs["nom"] = "Le nom est obligatoire.";
  }
  if (!filter_var($email, FILTER_VALIDATE_EMAIL)) {
    $erreurs["email"] = "E-mail invalide.";
  }
  if (!filter_var($age, FILTER_VALIDATE_INT, ["options" => ["min_range" => 14, "max_range" => 99]])) {
    $erreurs["age"] = "L'âge doit être entre 14 et 99.";
  }

  echo count($erreurs) === 0 ? "Inscription OK" : "Erreurs : " . count($erreurs);
?>
RENDU

Erreurs : 1

⚠️
Ne JAMAIS faire confiance aux données client

Le navigateur exécute « votre » page, mais l'utilisateur contrôle sa machine : JavaScript désactivé, maxlength ignoré, attribut required contourné, requête forgée directement. Validez toujours côté serveur ce qui a des conséquences : comptes, prix, droits. La validation HTML n'est qu'une ergonomie, pas une sécurité.

💡
empty vs isset vs === ""

isset répond « la clé existe » (elle renvoie false seulement pour null) ; empty renvoie true pour "", 0, "0", [] et null. Pour un champ texte, trim($v) === "" reste le test le plus explicite : attention, un zéro saisi dans le formulaire serait jugé « vide » par empty.

Dernier piège à connaître sur filter_var en mode validation : elle renvoie la valeur convertie en cas de succès et false seulement en cas d'échec. Or filter_var("0", FILTER_VALIDATE_INT) rend l'entier 0, une valeur « fausse » pour PHP : un test if (!filter_var(…)) rejetterait donc à tort un zéro parfaitement légitime. Écrivez toujours if (filter_var($v, FILTER_VALIDATE_INT) === false) quand le zéro est une saisie possible, et récupérez la valeur retournée — c'est désormais un int, plus la chaîne du formulaire.

04

Nettoyer / échapper

Deux mouvements différents, souvent confondus : nettoyer l'entrée — supprimer ce qui ne doit pas exister dans la saisie (trim, strip_tags) — et échapper la sortie — transformer les caractères dangereux en entités HTML au moment d'afficher (htmlspecialchars). Ce dernier point neutralise l'attaque XSS : un texte envoyé sous forme <script> ne s'exécute plus, il s'affiche tel quel.

PHP — Nettoyer puis échapper 
<?php
  // Champ "nom" rempli par un visiteur malveillant :
  $saisie = "Ali <script>alert('xss')</script>";

  $nom = strip_tags($saisie);     // retire les balises
  $nom = trim($nom);
  echo "Nettoyé avec strip_tags : $nom<br>";

  // Recommandé : conserver la saisie, échapper à l'affichage
  echo "Échappé avec htmlspecialchars : "
     . htmlspecialchars($saisie, ENT_QUOTES);
?>
RENDU

Nettoyé avec strip_tags : Ali alert('xss')
Échappé avec htmlspecialchars : Ali <script>alert('xss')</script>

⚠️
XSS : la règle d'or de l'échappement

Une seule protection compte : dès qu'une donnée fournie par un utilisateur est affichée dans du HTML, passez-la par htmlspecialchars($v, ENT_QUOTES, 'UTF-8'). Une balise <script> stockée puis affichée brute s'exécuterait pour chaque visiteur — vol de cookies, redirections, defacement. Nettoyez à la validation si besoin, mais échappez à chaque sortie, sans exception.

⚡ EXO FLASH Une saisie, trois sorties
  1. Créez nettoie.php et déclarez $saisie = '<b>Promo</b> du "vendredi"';.
  2. Affichez la saisie sur trois lignes : en brut, puis avec htmlspecialchars($saisie, ENT_QUOTES, 'UTF-8'), puis avec strip_tags($saisie).
  3. Prévoyez laquelle affiche « Promo » en gras et laquelle montre &quot; devant les guillemets, puis vérifiez avec « Afficher le code source » (Ctrl+U).
Voir un début de correction 
<?php
  $saisie = '<b>Promo</b> du "vendredi"';

  echo $saisie . "<br>";
  echo htmlspecialchars($saisie, ENT_QUOTES, 'UTF-8') . "<br>";
  echo strip_tags($saisie);
?>
05

Afficher les erreurs & réafficher les valeurs

Lors du post de formulaire vers sa propre page, on affiche le formulaire à nouveau, mais enrichi : chaque message d'erreur sous son champ, et la saisie de l'utilisateur conserve ses valeurs (value="…") pour qu'il n'ait pas à tout retaper. Les messages sont produits par la validation, stockés dans un tableau indexé par nom de champ.

PHP — formulaire.php (page unique) 
<?php
  $erreurs = [];
  $nom   = "";
  $email = "";

  if ($_SERVER["REQUEST_METHOD"] === "POST") {
    $nom   = trim($_POST["nom"] ?? "");
    $email = trim($_POST["email"] ?? "");

    if ($nom === "") {
      $erreurs["nom"] = "Nom obligatoire.";
    }
    if (!filter_var($email, FILTER_VALIDATE_EMAIL)) {
      $erreurs["email"] = "E-mail invalide.";
    }
  }
?>
<form method="post">
  <input type="text" name="nom"
         value="<?= htmlspecialchars($nom) ?>">
  <?= $erreurs["nom"] ?? "" ?><br>
  <input type="text" name="email"
         value="<?= htmlspecialchars($email) ?>">
  <?= $erreurs["email"] ?? "" ?><br>
  <button>Envoyer</button>
</form>
RENDU

Le nom « Sara » est conservé dans son champ ; seul message affiché sous l'e-mail : « E-mail invalide. » — l'utilisateur corrige sans tout retaper.

💡
Une page, deux vies

Charger la page sans POST = formulaire vide ; charger la page après POST = formulaire complété d'erreurs et de valeurs conservées. Le même fichier gère les deux vies grâce au test de REQUEST_METHOD. Détail d'usage : un champ type="password" reste volontairement vide après un échec — pour des raisons de sécurité, il n'est jamais réaffiché.

06

GET vs POST

Choisir la méthode, c'est choisir comment les données voyagent. Avec GET, la saisie devient des paramètres d'URL à la fin de l'adresse : visibles, partageables, bookmarkables — rafraîchir la page rejoue la même requête sans danger. Avec POST, les données voyagent dans le corps de la requête HTTP : invisibles dans l'URL et sans limite pratique de taille.

CritèreGETPOST
Transportparamètres accrochés à l'URLcorps de la requête HTTP
Visibilitétotale : barre d'adresse, historique, logs serveuraucune dans l'URL
Taillelimitée (≈ 2 048 caractères dans la plupart des navigateurs)pratiquement illimitée (configurée côté serveur)
Partage / indexationURL partageable et bookmarkablenon — requête non rejouable en un clic
Usages typesrecherche, filtres, navigation par paramètresinscription, connexion, envoi de fichiers, paiement
💡
POST pour tout ce qui est sensible

Règle mémorisable : GET lit, POST écrit. Un filtre de recherche, un tri, une pagination → GET (l'URL reste partageable). Une création, une modification, une connexion, un mot de passe — bref tout ce qui change d'état ou mérite la confidentialité → POST. Un mot de passe envoyé en GET apparaît en clair dans l'historique du navigateur et les logs du serveur.

07

Exercices pratiques

EX 01 👋 Bonjour, qui êtes-vous ?
  1. Créez exo_bonjour.php : un formulaire GET avec champs prenom et age.
  2. À la soumission, affichez « Bonjour X, tu as Y ans ».
  3. Observez l'URL : les valeurs y apparaissent. Testez age = 99 sans limite.

Indice : lisez $_GET["prenom"] et $_GET["age"] avec l'opérateur ?? pour éviter les erreurs de première visite.

EX 02 ✅ Validation d'inscription
  1. Reprenez le formulaire POST d'inscription (nom, e-mail, âge) vers lui-même.
  2. Validez : nom non vide, e-mail via FILTER_VALIDATE_EMAIL, âge entier entre 14 et 99.
  3. Affichez chaque erreur sous son champ au lieu d'un bloc unique.

Indice : un tableau $erreurs[nomDuChamp] = message indexé par champ, testé avec isset($erreurs["nom"]) sous chaque input.

EX 03 🛡️ Tester le XSS
  1. Affichez la saisie d'un champ message en brut (sans échappement).
  2. Envoyez dedans : <script>alert('test')</script> — constatez l'exécution.
  3. Refaites la même page avec htmlspecialchars : la balise s'affiche en texte.

Indice : la différence est uniquement dans l'affichage — la saisie n'a pas changé, seul son échappement à la sortie change.

EX 04 🔁 Formulaire réaffiché
  1. Faites un formulaire POST auto-expédiant (action vide) avec champ question et réponse en textarea.
  2. Si la réponse est vide, réaffichez le formulaire avec l'erreur et la question déjà tapée.
  3. Si tout est valide, affichez les deux valeurs échappées.

Indice : value="<?= htmlspecialchars($question) ?>" conserve la saisie — et <textarea><?= htmlspecialchars($reponse) ?></textarea> fait de même pour l'élément texte.

08

Bilan & mini-glossaire

Ce que vous maîtrisez

  • La structure d'un <form> : action, method et l'attribut name de chaque champ
  • Récupérer les saisies : $_GET, $_POST (et pourquoi $_REQUEST est à éviter)
  • Le test de REQUEST_METHOD pour distinguer visites et soumissions
  • La validation serveur : isset, empty, trim, filter_var
  • Le nettoyage des entrées (strip_tags) et l'échappement des sorties (htmlspecialchars)
  • Le réaffichage : erreurs par champ et valeurs conservées via value=""
  • Quand utiliser GET (lire, filtrer) et quand utiliser POST (écrire, sensible)
  • La menace XSS et la règle : tout affichage de donnée utilisateur passe par l'échappement
🚨
Erreurs fréquentes
  • Accéder à $_POST["champ"] sans test de méthode ni ?? → « undefined index » à la première visite.
  • Oublier l'attribut name sur un champ → sa valeur n'arrive jamais dans la superglobale.
  • Se fier à required ou type="email" HTML comme seule sécurité.
  • Afficher une saisie sans htmlspecialchars → XSS possible sur chaque visiteur.
  • Envoyer un mot de passe (ou toute donnée sensible) en GET → il finit dans l'URL, l'historique et les logs.
